# P2 단일 요청자 쓰기 전체 재측정

**E-24 마감(2026-11-10):** 새 세션 한 번의20개 쌍별 p95 비율은 모두≤1.10이나, 예열/본20구간 중5개가 CPU간섭으로 무효였다. **읽기·전체 viewport 채택, 쓰기는 개선 방향 확인·정량 판정 보류**로 P2를 마감했다. [E-24 B 결과](P2_WRITE_E24.md). 아래는 당시 기록이며 이전 판정을 소급 변경하지 않는다.

**후속 병기:** [E-23 표본300 결과·E-24 설계](P2_WRITE_E23.md). 이 문서의30표본 세션과 원본은 대체하지 않는다.

## 승인·고정 조건

사용자는 기존 읽기 E-16/E-21·전체 viewport 결과를 유효로 인정했다. 쓰기는 무효 B2만 교체하지 않고 **새 세션에서 A1/B 5쌍 전체**를 다시 실행한다. [기존 결과·무효 표본](P2_RESULTS.md)은 삭제하거나 새 표본과 합치지 않는다. P3는 진행하지 않는다.

- AB/BA 교대: A1/B, B/A1, A1/B, B/A1, A1/B. 단일 VU, 매 실행 새 JVM, 예열10+측정30 CRUD 주기. 총400주기/1,200 HTTP(본900·예열300).
- 기존 M 편향 seed·앱/DB/k6 이미지·CPU/메모리·heap·Hikari·PG 설정·간섭 판정은 불변. 새 Compose 프로젝트·결과 폴더 `*-write-retest1`을 사용해 이전 DB·원본을 보존한다.
- A1 SHA256 `da87c44168c321d1b05c5d3bbf61a459284c937fdd145c93aa6e940fff1d1a60`, B `639c3956667040fde1072d922d614c4b8a96c7c78c554957d9042c89175cef5e`. 애플리케이션 변경·재빌드 없음.
- 판정: 모든 예열/본 측정 유효·오류0·dropped0·업무 DB 복원, 쓰기 회귀10% 이내. 기존 p95 반복 변동 폭/중앙값10% 초과 시 승자를 선언하지 않는 규칙도 유지한다. endpoint당 회차30개로 p99는 작은 표본의 탐색값이다.
- 사용자 환경 확인 완료: 전원 연결·최고 성능·절전 해제·업데이트 일시 중지, **브라우저 포함 무거운 앱 종료 및 측정 중 미사용**. 시작/회차별 프로세스·전원 상태를 기록한다. 노트북 상대 비교이며 운영 절대 수치가 아니다.
- 같은 배경7개는 pause/unpause만 사용한다. before→paused→restored 상태를 별칭으로 남긴다. finally·부모 종료 감시자가 실패/중단에도 복구하며 마지막 직접 inspect로 모두 running인지 확인한다.

## 실행 전 시간 추정

이전 단일VU10회 측정 단계(스냅샷·수집 포함)의 합은 **953.462초**다. 여기에 기동10회×30초, 새 DB 시드/검증2회×60초, pause/복구60초를 더하면 **1,433.462초(23.89분)**다. 호스트 준비 편차를 포함해 **24~30분**으로 예상한다. 분석·문서화·업로드 시간은 별도다. 이 추정은 부하 시간이나 반복 수를 늘리는 설정이 아니다.

```powershell
$env:PERF_HEAVY_APPS_STATUS='closed-user-confirmed'
node perf/stage2/p2-session.mjs write-retest
# 비정상 종료 뒤 수동 복구가 필요한 경우에만
node perf/stage2/p2-session.mjs restore write-retest
```

## 후속 정리만 기록

명시적 `READ_COMMITTED`가 JDBC `SHOW TRANSACTION ISOLATION LEVEL`을 **요청당3회(한 CRUD9회)** 추가한다. 현재 기본 격리 수준과 같으므로 명시 제거를 별도 검토한다. 이번 재측정에서는 코드를 바꾸지 않으며, 제거 시에도 별도 잠금 SELECT 다음 DML의 새 snapshot·경합 정합성을 다시 검증해야 한다.

실행 코드 `39dc2b4666d03c3a2ed2deeb9c27e89623e60a99`, 앱 `91d653a`의 기존 이미지다. **10회 실행·예열 포함20구간 모두 유효, HTTP1,200건 성공·오류0·검사 실패0·dropped0**, 본 측정900건/예열300건이다. 10회 모두 CRUD 뒤 업무 DB fingerprint 일치·컨테이너 OOM0, 원래 M 시드와 같은 places fingerprint를 확인했다. 간섭 미검출은 관측 규칙을 통과했다는 뜻이며 간섭이 완전히 없었다는 증명은 아니다.

## 자원·복구·원본 보존

단일 요청자 k6 HTTP 처리율은 A1 5.56~5.77req/s, B45.75~52.87req/s였다. 도착률을 올려 탐색한 최대 지속 처리량이 아니며, HTTP 생성/이동/삭제가 섞인 값이다. Docker CLI 준비·호스트 관측 대기는 처리율에서 제외한다.

본 측정 자원 관측창의 CPU 평균은 A1 앱0.121~0.134코어/DB0.845~0.855코어, B 앱0.686~0.751코어/DB0.085~0.094코어다. 앱 working set 최고치는 A1 494.09MiB/B490.29MiB, DB399.69/369.25MiB다. 짧은 B 관측창에는 앞뒤 대기가 포함되므로 CPU 평균을 요청당 비용이나 동일 시간 부하의 절감률로 해석하지 않는다. 각 회차 원본에는 CPU·메모리·throttle·호스트 상위 프로세스·관측 간격이 포함된다.

같은 배경7개 `running→paused→running`, 복구 실패0. 종료 후22:21:37 KST 별도 Docker inspect로 모두 `Running=true / Paused=false / Status=running`을 확인했다. 이7개에는 stop/rm/볼륨 변경을 하지 않았다. 기존 파일4,328개 크기·mtime과 쓰기 관련379개 SHA256이 불변이다. 새 DB/원본 폴더만 사용했고 이전 결과와 합산하지 않았다.

## 검증 범위·분석 재현

앱 코드·JAR는 불변이다. 이 턴은 실행기·분석 도구·문서만 변경했으므로 allTests를 다시 실행했다고 주장하지 않는다. 직전 앱 전체 검증1,734건(성공1,733/실패0/기존HEIC skip1), 알려진 차이16건은 그대로다. 이번 도구 검증은39건 성공/실패0/skip0, 벽시계0.240초(Node0.184초)다. 공개 원본239개 파일에서 자격증명과 실제 배경 컨테이너 이름/ID가 없음을 검사했다.

`p2-write-report.mjs`는 새 세션의 예열/본20구간과5쌍을 모두 요구하고, 원래 시드·JAR·기본힙·SQL추적off·DB복원·복구 증거를 검사한다. 원본을 해당 build 폴더에 복원한 뒤 아래 명령으로 분석을 재현할 수 있다. 부하를 다시 실행하는 명령이 아니다.

```powershell
$env:PERF_SESSION='write-retest1'
$env:PERF_STAGE='p2-a1'; node perf/stage2/summarize.mjs
$env:PERF_STAGE='p2-b'; node perf/stage2/summarize.mjs
node perf/stage2/p2-write-report.mjs
node --test perf/stage2/*.test.mjs
```

분석 재현은 새 세션 원본과 기존 `perf-stage2-p2/writes-session.json`의 시드 fingerprint를 함께 사용한다. private 자격증명·응답 준비 캐시는 공개 압축에서 제외하고, 다른 프로젝트 이름/ID는 별칭으로 기록한다.
