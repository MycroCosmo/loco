# P0 기준선 결과

상태: **P0 완료·중단.** 대표 A5회 통과, 탐색6조건 중4개 통과·2개 예열 실패, CMS1회 통과. 이 문서의 pilot과 단회 탐색은 채택 근거가 아니다. **노트북 상대 비교이며 운영 절대 수치 아님.** P1~P3 구현과 E-10 지연 budget 확정은 이번 P0에 포함하지 않는다.

재검증 자료: [manifest](results/p0-20261108/manifest.json), [정상·실패12실행 요약](results/p0-20261108/summary.json), [압축 원본 Release](https://github.com/MycroCosmo/loco/releases/tag/perf-stage2-p0-20261108). 원본290파일·35,141,593 bytes, SHA256 `b19e883c72ac8b126462771e7e27be9b5dceee155ad7930d0372106679bbac02`. private/인증 정보·준비 응답 캐시·바이너리JFR 제외, 배경 컨테이너 이름 비식별 처리, 비밀값 검사와 파일별 SHA256SUMS 포함. 원본에는 pilot·예열·실패·진단도 남아 있으며 정상12개를 뜻하는 파일명이 아니다.

## What / Why

같은 v3에서 이후 누락 정합성·SQL·PostGIS 대안을 비교할 수 있도록 자원·seed·코드·요청·오류·업무 결과가 설명되는 A 기준선을 만든다. v2의 속도와 Java의 속도를 기술 선택의 효과로 비교하지 않는다.

## How — 준비 중 발견·수정한 문제

- 전용 BootJar에는 Java 타깃을 명시해야 했고, 제한된 단일 테스트 필터는 core 모듈까지 적용되므로 집중 검증에서는 core를 제외했다. 이후 전체 회귀에서 core125를 모두 실행했다.
- 일반 Docker ignore가 빌드 JAR도 제외하므로 전용 Dockerfile ignore에 측정 JAR만 허용했다. 내부 네트워크는 호스트 포트가 열리지 않아 준비용 HTTP를 docker exec/curl로 변경했다. 대표 HTTP는 k6→앱 직접 경로다.
- PostgreSQL 시작 인수의 `pg_stat_statements.track=none`이 ALTER SYSTEM보다 우선했다. 초기 SQL0건 진단은 **무효**로 원본을 보존하고, 시작 인수에서 제외한 뒤 진단 시 all/대표 시 none의 실제 적용을 assert한다.
- marker-cluster의 준비 요청을 실제 `cellLatKey/cellLngKey` 계약으로 바로잡았다. PostgreSQL이 `coalesce(...,0)`의 0도 파라미터로 정규화하므로 실제 관측 SQL에 맞춰 EXPLAIN 복원을 수정하고 회귀 검사를 추가했다.
- pg_catalog 메타데이터 조회는 기존 ORM SQL 카운터에 잡히지 않는다. `sqlCount`(업무), `driverMetadataQueries`, `postgresSelectCount`(전체 SELECT)를 함께 기록하고 BEGIN/COMMIT도 원본에서 보존한다. 높은 전체 DB 호출을 숨겨 기존 예산과 같다고 보고하지 않는다.

10%에서는 SQL이4,999개 셀을 반환한다. `ORDER BY count DESC`에 동률의 2차 정렬이 없고 Java가 앞699개를 선택한 뒤 나머지를overflow로 합친다. 부하 후 실제 HTTP3회에서 준비 응답과 **표시 장소2개·overflow 중심 좌표가 달라지고 전체count4,999는 같음**을 확인했다(`overflow-probe.json`). 배열 순서만 정규화하는 기존 검사는 이 실제 내용 차이를 제대로 거절했다. v2 코드도 `count DESC`와699개 분리를 사용한다. 이번 P0에서 대규모 v2 HTTP를 다시 관측한 것은 아니므로 v2의 동일 실패율을 주장하지 않는다.

전체 범위에서는 `SELECT *`가5만 셀을 읽고 Java에서699개/overflow를 만든다. 동시 요청 중 JDBC 결과를 가져오다가 `java.lang.OutOfMemoryError: Java heap space`가 발생했다(`overflow-app.log`). **컨테이너 OOMKilled=false와 JVM heap OOM은 다르다.** 이후 준비를 중단하고 같은 JAR·힙·자원으로 측정 앱만 재시작한 뒤 독립 조건의 예열부터 진행했다. 두 실패 조건 모두 업무 DB 불변을 별도로 확인했다. 서버 정렬·쿼리·힙을 바꾸지 않았으므로 알려진 차이 등록은 기존11건 그대로다.

## Opinion — 기술 판단과 다음 결정

주 조건의 A 기준선은 응답·데이터 불변·반복 편차 검사를 통과했다. **개선안 B의 채택이나 운영 용량 판정은 하지 않았다.** 큰 viewport의 실패는 제외해 숨길 대상이 아니라 다음 비교의 제약이다. 현재 기본 힙/Serial GC/Hikari 설정을 미튜닝 기준으로 보존했으며, 설정이 원인인 조건에서 PostGIS의 우열을 선언할 수 없다. E-10 지연 budget은 사용자와 P0 결과를 검토한 뒤 B 실행 전에 확정한다. P1~P3는 시작하지 않고 여기서 멈춘다.
