# E-14 ROUND 인덱스·E-15 같은 세션 대조

상태: **E-14 구현·검증 완료. E-15 같은 세션에서도 1% 회귀가 재현되어 성능 채택 보류. SQL·JFR 진단 후 중단했다. P2·P3 미진행.** 아래 실행 계약은 측정 전에 커밋 `8e1a9dd`로 고정했다.

## 결정과 가설

- **E-14 그룹 ROUND 역조회 인덱스**: group numeric ROUND6, cluster ROUND1/2/3::text와 같은 표현식 인덱스 4개를 V8로 추가한다. 원본 좌표·V1~V7은 불변이다. 범위 재작성은 float8→numeric 변환·음수 경계의 재현 위험, 생성 컬럼은 스키마·저장 증가 때문에 미채택했다.
- WHERE 식을 유지하고 cluster 정밀도만 검증된 1/2/3 SQL 상수로 만든다. 바인드된 정밀도는 generic plan에서 특정 표현식 인덱스와 맞지 않는다. 기본 planner·JDBC 설정은 변경하지 않는다. custom/generic 계획 모두와 경계 oracle를 검사한다.
- **E-15 P1 1% 회귀 판정**: 역사적 수치 대신 같은 세션 P0 측정 JAR와 P1+E-14를 AB/BA 5쌍 비교한다. 1% 50req/s·10% 16req/s, M 편향·hot80%, 기본 힙/CPU/RAM/풀 동일. 1% p95 또는 p99 중앙값 회귀가10%를 넘으면 JFR·SQL 진단 후 중단한다. 넘지 않으면 이전 역사적 회귀를 세션 편차로 기록하되 원인을 단정하지 않는다.

## 측정 전에 고정한 방법

P0는 c7320e6 결과에 연결된 기존 이미지 `sha256:985c8f260403246086c1063fb04abc5951303af3d2419706d6e305a13b5a7306`, JAR `c1a5293f1dc59a6ee0e648548e92695857a0357c57d10e45f06704a96952158f`를 그대로 사용한다. 현재 소스로 재빌드하거나 정렬 패치를 넣지 않는다. A/B는 새 `loco-perf-e15-a/b` DB·출력 경로를 사용해 P0/P1 원본·볼륨을 보존한다. A는 V6, B는 V8까지 각 JAR의 실제 마이그레이션을 적용한다. 데이터는 동일 고정 seed SQL이다.

매 측정마다 비활성 쪽 앱/DB를 중지하고 활성 쪽 JVM을 새로 기동한다. 실제 JAR 해시·자원·전원 연결·최고 성능 모드를 검사하고, 동일 preflight→목표 도착률120초 예열→300초 측정을 수행한다. pair1/3/5는 AB, pair2/4는 BA이며 각 pair에1%·10%를 모두 측정한다. warmup/본 측정 오류도 보존하고 유리한 재시도를 하지 않는다. 무거운 앱은 사용자가 2026-11-09 종료 완료 및 측정 중 미사용을 확인했다. 기존 배경 컨테이너는 임의 종료하지 않고 자원 사용을 기록한다. 노트북 상대 비교이며 운영 절대 수치가 아니다.

P0 10% overflow의 동률 선택은 이미 E-12에서 승인된 차이다. 두 버전 모두 M singleton 셀에서 표시699개가 전체 유효 집합의 중복 없는 원소인지, 이름·좌표·count·응답 필드가 맞는지, 남은 전체count·가중 중심이 정확한지 검증한다(부동소수 합산 오차1e-10). B는 결정적 전체 hash도 검사한다. 1%는 양쪽 모두 전체 hash를 유지한다. 이 예외를 다른 데이터셋/오류에 확대하지 않는다.

대표 부하 시간은2조건×5쌍×2버전×420초=8,400초(140분). 전체 회귀 약20분·준비/계획·쓰기 비용 포함180~210분 예상, 회귀가 남으면 별도 JFR 진단 약10분 이상 추가다. p95≤200ms·오류0·dropped0, 회귀10%와 별도로 실행 간 range/median도 기록한다. 실패·표본 부족·변동이 크면 성능 채택 보류이며 최대 처리량 탐색은 이번에 하지 않는다.

쓰기 비용은 **같은 B JAR·M DB에서 V8 인덱스 없음/있음**만 교대5쌍으로 분리한다. 실제 HTTP POST→좌표 PUT→DELETE,1 VU·10회 예열·30회 측정/쪽(연산당150표본)을 사용한다. hot map의 별도 합성 음수 좌표로 원래 데이터에 영향 없이 실제 저장·셀 갱신을 거친다. 단일 사용자 비용 탐색이므로 p99나 동시 쓰기 처리량의 채택 근거로 삼지 않는다. 별도5회/쪽 SQL 추적으로 연산별 SQL 실행 시간·WAL·인덱스 크기를 기록하고 대표 HTTP 구간에서는 SQL 추적을 끈다. 진단용 DROP/CREATE는 새 B 실험 DB에만 허용하며 마지막에 V8 정의를 복구한다. 운영 Flyway 이력을 수정하지 않는다.

## 검증·실행 도구

- `V8__index_marker_round_lookups.sql`: 동일 ROUND 조회식 인덱스, 앱 기동 시 Flyway로 적용. 일반 CREATE INDEX는 빌드 중 쓰기를 막으므로 실제 전환에 유지보수 창이 필요하다. 데이터 손실 없이 제거할 수 있지만 과거 migration을 수정하는 rollback은 하지 않는다.
- `MarkerRoundIndexIntegrationTest`: V7→V8 원본 불변·재실행0,10만 장소에서 네 인덱스의 custom/generic 계획과 음수/경계 업데이트 결과를 강제 전체 스캔 oracle와 대조한다. 일반 계획은 scan 옵션을 강제하지 않는다. 기존 실제 HTTP 경계31개 테스트도 실행한다.
- `overflow-contract.js`·테스트: 알려진 비결정적 선택만 허용하며 잘못된 원소·중복·값·합계를 거절한다. k6와 Node 준비 검증이 같은 계약을 쓴다.
- `paired.mjs`:20개 측정의 순서·재기동·artifact·전원 조건·결과 보존을 고정하고 session manifest를 남긴다. 재실행은 기존 session을 덮어쓰지 않고 실패한다.
- `run.mjs write-cost`: 실험 전용 DB에서만 인덱스 유무의 실제 쓰기 지연과 별도 SQL 비용을 비교하고 원래 데이터를 확인한다.
