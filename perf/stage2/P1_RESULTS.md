# P1 좌표 정합성·결정적 overflow 기준선

상태: 구현·전체 회귀 완료, 성능 측정 진행 중. 미측정 값을 성공으로 간주하지 않는다. [결정·전환 계약](../../apps/server-v3/PERF_STAGE2_DESIGN.md), [P0 원본](P0_RESULTS.md).

## What · Why

PG numeric ROUND·0 정규화를 쓰기·그룹·셀 조회에 적용하고 V7으로 기존 셀을 재생성한다. JS toFixed와 PG의 경계 차이로 `37.05`, `-0.00001` 장소가 누락됐기 때문이다. count 동률의 셀 키2차 정렬은 표시699개와 overflow를 고정한다. 과거 v2 fixture는 유지하고 승인된 개선 차이2건을 따로 기록한다.

## How · 검증 범위

- 실제 POST→PUT→DELETE: 좌표31경계, 각 precision의 키·count·마커/cluster/group 조회. 300/301장소, 699/700/701셀 전환.
- 물리적 행 순서 변경: v2 표시 결과 변경을 관측하고 v3 전체 응답 동일성을 검사한다.
- V7: 누락·잘못된 키·음수0 셀 재생성, 장소 원본/V1 불변, 실패 시 DELETE까지 롤백, 재실행0.
- 집중 검증: 빠른40 + v2비교160 = **200성공·0실패**,120.672초. 첫 비교에서6자리 반 경계·음수0의 승인된 응답 차이2건을 확인한 뒤 v2 원본 보존+v3 새 계약으로 각각 검증했다.
- 전체 회귀 첫 실행1,130.133초: root416건(실패0·기존skip1), v2비교1,153건 중4실패. 생성/수정의37.05·-0.00001 DB 셀을 옛 v2와 같다고 하던 검사가 E-5 차이를 검출했다. v2 누락 관측은 유지하고 해당 새 셀의 전체 필드를 명시 검증하며, 다른 셀·업무 테이블은 완전 비교한다. 이 검증 보완에 따른 재실행 시간은 최초110~125분 예상에 추가된다.
- 경계 비교 보완 후 생성·수정75건 성공·0실패,72.707초. 추가 테스트 제외나 v2 fixture 수정 없이 통과했다.
- 최종 `perfBootJar allTests build`/Spotless: **1,694건 = 성공1,693·실패0·기존 HEIC skip1**, **1,222.358초**. core125건은 P0에서 실제 통과한 결과를 UP-TO-DATE 재사용, root416·v2비교1,153건은 재실행했다. v2 빌드1·기동1·재시작17·인증 대기0. 알려진 차이13(개선8·의도5·보류0), 기존11 case ID 유지. 준비 중 P1 컨테이너 기동·seed도 수행했으며 이 시간은 부하 측정과 구분한다.
- Node 도구12건 성공, 실제 일반/측정 JAR 격리4건 성공. V7 포함·운영 CoordinateKeys 클래스 없음 확인.
- 실제 P1 이미지에서37.05/-0.00001 모두level5/6/9/11 표시. M10만 장소의 좌표 키60만 검사 불일치0, precision별 count 합10만. hot/일반 마커4/3 SELECT, 그룹3·클러스터5 SELECT 유지.
- 성능 결과는 완료 후 아래에 기록한다.

## 측정 계약

M10만 장소·1천 방·편향·hot80%, viewport10%가 개선 판정용 새 A다. p95≤200ms·오류0·dropped0에서5회300초 측정(각 예열120초). viewport1%는50req/s5회로 P0 대비 p95/p99 회귀10% 이내를 검사한다. 전체 범위는 OOM·메모리 스트레스다. 기본371.25MiB 힙, 앱2CPU/1.5GiB·DB2CPU/4GiB/shared_buffers1GiB를 유지한다. P1은 전체 셀 물질화를 줄이지 않는다.

실행 전 예상110~125분(구현 제외). P0 `loco-perf-p0`/`build/perf-stage2`와 P1 `loco-perf-p1`/`build/perf-stage2-p1`을 분리한다. 실패 probe·원본을 지우지 않는다. 노트북 상대 비교이며 운영 절대 수치가 아니다.
