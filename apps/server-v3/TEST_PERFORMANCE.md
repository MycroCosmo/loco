# 전체 회귀 시간과 재시작 조건

Windows Java 21·Gradle 8.14.6·Docker Desktop, v2 이미지와 Prisma/libvips 도구 캐시가 있는 상태에서 측정했다. 각 실행은 빠른 테스트와 전체 비교 테스트, 포맷 검사와 빌드를 포함한다. 단일 실행의 wall time이며 부하가 다른 환경의 성능 보장은 아니다.

이전 작업 기록은 955.571초·v2 재시작 321회다. 당시에는 구간 계측이 없어 그 시간을 소급 분해할 수 없다. 이번 동일 계측 전후는 아래와 같다. 재측정 전 총시간이 이전 기록보다 길어진 이유를 특정 구간의 회귀로 단정하지 않는다.

| 구간 | 개선 전(초) | 개선 후(초) |
| --- | ---: | ---: |
| v2 재시작·HTTP 준비 | 750.387 | 13.482 |
| DB 초기화·시드·메일 비우기 | 59.870 | 55.383 |
| 실제 HTTP 요청(아래 이미지 구간 제외) | 34.803 | 26.399 |
| 이미지 메타데이터·변환·저장 | 16.718 | 14.717 |
| 기타 | 400.090 | 357.705 |
| 전체 | **1261.867** | **467.687** |

동일 계측 전후 794.180초(62.94%) 감소했다. 기존 955.571초 기록과 비교하면 51.06% 짧다. 기타에는 Gradle·컨테이너 최초 기동/종료·Spring 기동·DB 스냅샷 비교·Node 검증·파일 fixture 준비·독립 코덱 probe 등이 포함된다. 이 안의 세부 비용은 아직 분리 측정하지 않았다. [계측 경계](COMPARISON_TESTS.md#실행-시간-계측)를 참고한다.

## 재시작 원인과 변경

기존 CompatibilityTestBase의 BeforeEach는 usesV2Http=true인 모든 케이스에서 무조건 restart했다. 요청 제한에 걸리는지를 판단하지 않았다.
실제 v2 이미지의 ThrottlerGuard.generateKey는 컨트롤러·핸들러·기본 throttler 이름·IP로 키를 만든다. 따라서 기본 120/분도 애플리케이션 전체 공용 한도가 아니다. 다른 지도 ID나 OAuth provider는 같은 핸들러 한도를 공유하며, 같은 URL의 GET/PUT은 다른 핸들러다. 이 동작은 새 필수 HTTP 비교로 검증한다.

현재는 v2가 반환하는 실제 키·경로 패턴·잔여 횟수를 관측한다. 첫 요청의 잔여량이 없거나, 429 경계 검증에 초기 한도가 필요하거나, 동시 요청에 필요한 슬롯이 부족할 때만 시나리오 시작 전에 재시작한다. 오류 응답을 받은 뒤 재시도하지 않는다. 깨진 JSON처럼 Guard 이전 거절은 소비한 요청으로 세지 않는다. 시나리오 도중 소진되면 재시작 대신 만료를 기다린다.

개선 후 실제 6회:

| 사유 | 횟수 |
| --- | ---: |
| 동시 재설정 2개 슬롯 확보 | 1 |
| reset-password 잔여량 소진 | 1 |
| forgot-password 잔여량 소진 | 1 |
| forgot-password 429 경계 검증의 초기 한도 확보 | 1 |
| 핸들러 독립성 검증의 login 10개 슬롯 확보 | 1 |
| login 429 경계 검증의 초기 한도 확보 | 1 |

인증 외 API 재시작 0회, 시나리오 내부 대기 0ms였다. 준비용 JWT 직접 서명, DB 초기화와 전체 스냅샷 비교, 필수 429·동시 요청·이미지 검증은 유지한다. v2 운영 소스·요청 제한값·IP를 바꾸지 않았다.

## v2 계측의 동작 보존 원칙과 확인 방법

`src/test/resources/compat/timing-v2.cjs`는 **v2가 실제 계산한 값과 실행 시간을 관측하며 업무 동작을 바꾸지 않는다**. 요청 제한을 우회하거나 테스트 기대값에 맞추는 대체 구현이 아니다.

- `UploadService.saveAsWebP`를 같은 `this`와 인자로 한 번 호출하고 반환 값·예외를 그대로 전달한다. `finally`에서는 경과 시간만 기록한다. 이미지 입력·변환 옵션·출력 파일·DB를 바꾸지 않는다.
- `ThrottlerGuard.generateKey`의 원래 반환 값을 그대로 사용한다. 핸들러 이름·경로 패턴을 읽을 뿐, 키·IP·한도·TTL·카운터를 고치거나 429를 다른 응답으로 바꾸지 않는다.
- HTTP 처리도 원래 함수를 호출한다. 테스트 전용 `X-Harness-Image-Nanos`, `X-Harness-Handler`, `X-Harness-Route` 헤더와 계측 비용은 추가된다. 따라서 “응답 바이트와 실행 시간이 완전히 같다”는 뜻은 아니다. 상태·업무 JSON·기존 헤더의 의미·DB·파일 결과를 보존한다.
- 이 파일은 `SharedHarness`가 Testcontainers에 복사하고 `NODE_OPTIONS`로 주입한다. `start-v2.cjs` 실행에서만 활성화된다. v2 운영 소스·개발 Compose·운영 이미지에 계측을 넣지 않는다. 하네스의 컨테이너 재시작 판단은 별도 Java 코드의 책임이다.

확인 방법:

1. 정적 확인: 위 래퍼가 원래 함수를 정확히 한 번 위임하는지, 성공 값과 예외를 바꾸지 않는지 확인한다. 저장소 루트에서 `git diff -- apps/server infra/docker`로 운영 코드 변경 여부를 확인하고, `rg -n 'timing-v2|harness-timing|NODE_OPTIONS' apps/server-v3/src/test infra`로 주입 위치를 찾는다. Boot JAR에도 테스트 계측 파일이 없어야 한다.
2. 동작 확인: 같은 v2 이미지에 계측 **미주입/주입** 두 실행을 만들고 각각 DB·파일·메일·요청 제한 상태를 동일하게 초기화한다. 정상/잘못된 입력/인증 실패/없는 경로, 이미지 성공·변환 실패, DB 오류, 핸들러별 한도 직전·429·다른 핸들러 요청을 동일 순서로 보낸다. 상태·JSON 구조와 값·DB·파일·메일 결과 및 기존 요청 제한 헤더를 비교한다. 추가 `X-Harness-*` 헤더와 사전에 지정한 시간·생성 ID만 정규화하며, 429 여부나 오류 문구를 제외하지 않는다. TTL·Date 등 시간 의존 헤더는 같은 의미와 유효 범위를 검증한다.
3. 하네스 회귀: `./gradlew.bat test comparisonTest --rerun`으로 핸들러별 잔여량 관리·필수 429·이미지·실패 경로가 계속 통과하는지 확인한다. 이 검증은 계측된 v2와 v3의 호환성을 확인하며, 위 미주입/주입 A/B 검증을 대신하지 않는다.

현재 완료한 것은 래퍼·주입 위치의 정적 확인과 아래 기록된 전체 회귀다. 계측 미주입/주입 전용 A/B 자동 검증은 아직 없으며 이번 문서 변경에서 실행했다고 주장하지 않는다. 앞으로 계측 래퍼를 변경할 때에는 위 A/B 절차까지 확인한다.


스크립트는 test/comparisonTest를 실제 재실행한다. 원본 로그·시간·테스트 식별자는 build/performance/<Label>/에 있다. 기록한 before는 하네스 회귀 8건을 추가하기 전 실행이므로, 현재 코드로 each-case를 재현하면 추가된 테스트도 함께 돈다. 기본 gradlew test/comparisonTest/allTests/build의 검증 범위는 그대로다.
