# P3 설계 — PostGIS 표현식 GiST와 남은 DB 작업량

2026-11-10. **E-25~E-32 승인, 구현·검증 후 선별 측정 환경 확인 대기.** 아래 과거 선택지는 이력이며 맨 위 확정 결정이 우선한다. 선별/정식 측정은 아직 실행하지 않았다. 브랜치는 `feature/perf-stage2`, 출발점은 `8f2c07c`의 P2 마감이다.

- E-27 A: §5 지연·DB CPU/요청·버퍼 필수 기준 유지.
- E-28 A: READ_COMMITTED 명시·SHOW 제거는 P3와 분리.
- E-29 A: P2 B 원래 JAR 대 공간 B, A-ext 단회 진단.

### E-32 정식 측정 전 선별 단계

1. 구현, §3 전체 정합성 oracle, allTests build는 필수이며 선별 미달로 생략하지 않는다.
2. 동일 M seed·hot 지도방의 주 조건 셀 SQL EXPLAIN(ANALYZE, BUFFERS) **A/B 각3회**, 10%·16req/s HTTP **A/B 각1회(예열120+본300초)**를 실행한다. 읽기 단회 선별은 정식 채택 근거가 아니다. 첫쌍 순서는A→B, 계획도A/B 교대로3쌍을 사전 고정한다. root Shared Hit+Read를 사용하며 하위 버퍼를 합산하지 않는다.
3. **버퍼3회 중앙값 B≤A×0.80 AND 단회 p95 B≤A×0.80**일 때만 §8 정식 측정으로 진행할 수 있다. 통과를 P3 채택으로 기록하지 않는다. 정식 측정에서 §5 전체 기준을 다시 판정한다.
4. 유효한 선별이 미달이면 정식 측정·E-30 쓰기 측정 없이 **“이 데이터·경로에서 공간 인덱스 이점 작음, 기존 B-tree로 충분”**으로 P3를 마감한다. 이는 현재 seed·경로·부하에 한정된 결론이며 다른 데이터의 우열을 일반화하지 않는다. 간섭/오류/DB복원 실패 등으로 무효이면 성능 미달로 해석하지 않고 E-31에 따라 중단·VM 재검토한다.
5. 선별도 §7 앱 완전 종료·자동 업데이트 확인, 분리 실행기·Codex 완전 대기를 적용한다. 이번 작업은 구현·검증·커밋·push 후 환경 확인 요청에서 멈춘다.
6. 전체 viewport의 모든 셀 집계 병목은 P3 밖이다. **후속 실험 후보: 사전 집계·캐시**, 무효화/동시 갱신/정합성 계약부터 별도 설계한다. Redis 도입 승인으로 간주하지 않는다.

선별 예상은 A/B HTTP2×485초≈16.2분+seed/확장/계획/복구 약8~14분으로 **24~31분**이다. 정식은 선별 통과 시에만 별도 §8 예상4시간40분~5시간20분이며, 결과를 본 뒤 행렬·힙·판정·예열을 바꾸지 않는다. 선별과 정식 원본/manifest는 분리한다.

## 1. What·Why와 확정된 경계

P2는 **읽기·전체 viewport 채택, 쓰기는 개선 방향 확인·정량 판정 보류**로 확정한다. E-24와 이전 쓰기 결과를 소급 통과시키지 않는다. 앱 메모리의 전체 셀 물질화는 해결했지만 전체 viewport의 DB CPU 약1.34코어와 p95 약117ms가 남았다. P3의 가설은 **선택적인 viewport에서 표현식 GiST가 후보 셀/장소와 버퍼 접근을 줄일 수 있다**는 것이다. 전체 범위에서 공간 인덱스가 자동으로 빨라진다는 가설은 세우지 않는다.

- E-8 A 유지: 기존 좌표의 표현식 GiST. geometry 업무 컬럼·공간 read model·좌표 backfill은 추가하지 않는다. JPA native query를 사용한다.
- P2의 301 후보, DB top699+overflow, 한 snapshot, E-12 결정적 정렬, E-20 중심 좌표 계약, E-22 잠금 SELECT→DML→커밋을 보존한다.
- P4 이미지·Redis·CMS 인덱스·캐시·전체 범위 집계 캐시·힙 증설은 범위 밖이다.
- Opinion은 결과 후 사용자가 작성한다. 아래 성공 수치는 선택 후 결과 전에 커밋으로 고정한다.

전체 범위에서는 top699 선택과 overflow 중심 계산이 거의 모든 대상 셀을 요구한다. GiST는 후보를 제거할 수 없고 추가 비용이 생길 수도 있다. 이 한계가 **10% 주 판정 권장** 근거다. 전체 범위의 DB 작업량 감소에는 별도 집계 알고리즘이 필요할 수 있으며 P3에 몰래 추가하지 않는다.

## 3. 공간 표현과 정합성

개념 식이며 실행할 DDL은 아니다.

- places: `ST_SetSRID(ST_MakePoint(longitude, latitude), 4326)` 표현식 GiST.
- cells: `ST_MakeEnvelope(minLng, minLat, maxLng, maxLat, 4326)` 표현식 GiST. 셀 평균 중심은 인덱스 경계가 아니다.
- viewport도 경도 X·위도 Y 순서의 envelope. geometry를 쓰며 geography·거리·투영 변환·좌표 정규화는 도입하지 않는다.
- 후보는 `expression && viewport`로 좁히고, **기존 double precision의 네 숫자 비교와 mapId/precision 조건을 모두 유지**한다. GiST bbox의 근사 표현에서 생기는 추가 후보를 기존 조건으로 제거한다. 연산자·플래너가 경계에서 false negative를 만들지 않는지 oracle로 검증한다. `ST_Contains`로 경계를 제외하거나 `ST_Intersects`의 새로운 도형 의미로 바꾸지 않는다.
- 기존 min/max 교환, PrismaFloats 입력, 유한수 검사·잘못된 입력 응답을 유지한다. 날짜변경선 횡단을 자동 분할하지 않는다. SRID4326 지정만으로 기존 범위 밖 유한 좌표를 새로 거절하지 않는다. 현재 허용 입력을 표현 못하면 새 E-번호로 멈춘다.
- mapId/precision의 기존 B-tree·V8 인덱스를 유지한다. 별도 bbox GiST와 BitmapAnd를 선택할지는 플래너에 맡긴다. `btree_gist` 추가·복합 GiST·부분 인덱스는 이번 권장안에 포함하지 않는다. 같은 위치의 여러 방 데이터에서는 global GiST 후보가 늘 수 있음을 탐색한다.

정합성 검사는 R 고정 seed+경계 생성 사례로 A/B 전체 JSON을 비교한다. 좌표37.05·−0.00001·−0.0, 경계에 정확히 접한 점/선 형태 셀, bbox는 겹치지만 중심은 밖인 셀, 300/301·699/700/701, 양쪽 반구·뒤집힌 범위·빈 범위·아주 좁은 범위·큰 유한값, precision1/2/3, level 분기, 동률·행 순서 변경을 포함한다. 태그 등 현재 무시되는 query도 갑자기 필터로 만들지 않는다. 필터 결과·count·키·표시 집합·순서 완전 일치, 중심만 기존≤1e-10 허용이다. 응답 차이가 나면 허용 오차를 넓히지 않고 중단한다. 의도적 응답 변경은 별도 승인·알려진 차이 등록이 필요하다.

## 4. 비교군과 DDL 계획

권장 E-29 A:

- **A = P2 B 원래 JAR** SHA256 `639c3956667040fde1072d922d614c4b8a96c7c78c554957d9042c89175cef5e`, 앱 구현91d653a. 기존 V1~V9 스키마·인덱스, READ_COMMITTED 명시 유지.
- **B = 동일 코드에서 승인된 공간 predicate·표현식 인덱스만 추가**. 다른 튜닝·재집계·정렬 변경 없음. 확장·인덱스·query를 합친 P3 변경의 효과이며 순수 인덱스 한 요소만의 효과라고 부르지 않는다.
- 별도 준비 DB에서 extension만 설치하고 기존 SQL을 실행하는 A-ext 단회 계획 확인은 확장 설치 영향 진단용, 채택 근거가 아니다. A의 정식 DB는 건드리지 않는다.
- 양쪽 같은 Postgres17/PostGIS3.6 이미지 **digest**, seed·row fingerprint·ANALYZE 절차, 재시작·예열·Hikari·work_mem·heap·GC를 고정한다. B 확장은 Flyway 다음 가용 버전(현재 V9 다음 **V10 예상**)으로만 관리한다. 기존 V1~V9 수정 금지.
- 로컬 실험 DB에서 일반 CREATE INDEX의 시간·크기·쓰기 차단 시간을 기록한다. 운영 적용 시 CONCURRENTLY/무중단 배포는 별도 계획이며 이번 실험이 운영 배포 승인은 아니다.
- Flyway V1 target1 Prisma 일치 검사는 계속 V1만 검사한다. 현행 스키마의 'PostGIS 없음' 검사는 명시 승인된 V10 전/후 계약으로 구분한다. 확장 메타 테이블을 업무 DB fingerprint에 무작정 추가하지 않는다. 데이터 테이블·열·기존 API는 불변이다.

## 5. How — 사전 판정 제안

**기존 유효성·읽기 판정 산식은 유지**한다. 예열120초+본300초, side별 p95 range/median≤10%, 오류0·dropped0·p95≤200ms, 간섭 규칙 불변. 읽기는 회차별 p95/p99의 중앙값 비율로 판정하고 쌍별 값도 모두 공개한다. E-24의 pair별 강제 규칙은 쓰기에만 적용한다. 신뢰구간·부트스트랩을 추가하지 않는다.

| 항목 | E-25 A / E-27 A 권장 기준 |
| --- | --- |
| 주 판정 | M·편향·hot80%·**10% viewport·16req/s**, A/B5쌍 AB/BA. B p95 중앙값≤A×0.80, p99≤A×1.10 |
| 1% 회귀 | 같은 세션 P2 B(A) 대비 **1%·50req/s, 5쌍 p95·p99 각각≤1.10**. 과거 P0/P2 수치는 맥락으로만 병기 |
| 전체 범위 | 16req/s A/B3쌍 AB/BA/AB, p95·p99≤A×1.10, OOM·오류·dropped0. 채택 개선 근거가 아닌 악화 방지/메모리 검사 |
| 메모리 | 같은 동시성에서 P2 JDBC 상한(후보301+셀700) 유지,1%/10%/전체 할당·GC 별도 진단. 셀 수에 비례하는 앱 물질화 재도입0. heap389,283,840바이트 유지 |
| DB 비용 | 주 조건의 **본300초 DB CPU-seconds/성공요청** 5회 중앙값 B≤A×0.90. 평균 코어·p95/max도 공개. 1%/전체 CPU/요청 악화≤10% |

| 결과 불충족 | p95만 개선됐으나 CPU/버퍼 필수가 실패하면 부분 성과/보류. 인덱스 사용 자체는 성공 조건 아님. 무효 회차 제외·교체·자동 재실행 없음 |

10% 과거 p95를 대입한 약16.545ms는 참고치일 뿐 고정 절대목표가 아니다. 실제 한계는 같은 세션 A×0.80이다. 전체를 주 판정으로 선택하면 약117→93.6ms가 참고 크기이나 역시 새 A를 사용한다. 결과 후 더 유리한 viewport·CPU·버퍼 기준으로 갈아타지 않는다.

EXPLAIN의 주 판정 대상은 고정 seed의 hot 지도방·10% viewport에서 실행한 셀 조회 SQL이며, 바인딩을 실행 전 manifest에 고정한다. 나머지 cold 방·individual·group·cluster 계획은 보조로 모두 보존한다. 여러 plan 중 가장 좋은 것만 고르지 않는다. DB CPU/요청은 전체 hot80% 혼합 부하의 값으로, 단일 hot SQL 버퍼와 동일 지표로 합산하지 않는다.

버퍼는 물리 디스크 I/O와 같지 않다. hit도 반복 접근 비용이다. EXPLAIN ANALYZE의 시간·BUFFERS 계측을 HTTP 대표 지연에 섞지 않는다. 통계 변경/ANALYZE·plan cache·generic/custom plan을 양쪽에 동일하게 기록한다. plan 비교에서 하위 노드 합을 root와 더하지 않는다. warm-cache 측정이며 OS 캐시를 임의 삭제하지 않는다. cold-cache는 이번 범위 밖이다.

정식 SQL 수는 실제 HTTP별 기존 상한 그대로 고정하고 공간 predicate 때문에 N+1을 추가하지 않는다. group/cluster는 V8 계획·응답 회귀, CMS는 기존 조회 기준만 확인한다. 예상 성능 향상으로 새 SQL 수 상한을 임의로 바꾸지 않는다.

## 6. 쓰기 비용과 READ_COMMITTED 분리

표현식 인덱스는 INSERT/좌표 UPDATE 및 셀 갱신마다 유지 비용을 추가한다. 기존 E-22 교차 이동200/200·deadlock0, N=2/4/8/16 stale0, 없는 셀·삭제·커밋 실패 테스트를 재검증한다. 인덱스 생성시간·크기, SQL 실행시간·WAL·buffer·HOT update 영향은 진단으로 분리한다.

E-30 A 권장: P3 A/B 단일VU5쌍 예열10+본300 CRUD. E-24와 동일하게 생성/이동/삭제/혼합 각5쌍 p95 B/A≤1.10 필수, side p95 편차10%는 경고만. 오류·간섭·dropped·DB복원 실패는 무효, 표본 대체 없음. p99와 동시1/2/4/8/16 각1회는 탐색 보고로만 두며 정합성 테스트는 별도 필수다. **P2 쓰기 정량 판정을 재개하는 것이 아니라 P2 B→P3의 추가 인덱스 비용을 판정**한다. 유효성 미달이면 P3 쓰기 안전성 정량 판정도 보류한다.

`MarkerCells`의 명시 READ_COMMITTED는 잠금 획득 후 별도 DML이 새 snapshot을 보도록 보장한다. JDBC SHOW 요청당3회는 현재 기본 격리 수준과 중복일 수 있지만 제거하면 connection pool/호스트 설정에 의존하게 된다. **E-28 A: P3 A/B 모두 그대로 두고 이후 독립 변경으로 검증**한다. 별도 제거 실험에서는 실제 기본 격리 수준·pool 재사용/반납·SHOW wire 수·3커밋·강제 DB gate 경합을 재확인한다. SHOW 제거와 GiST를 한쪽에만 섞어 쓰기 개선을 주장하지 않는다.

## 7. 간섭 재발 방지 — 사용자 확정 사항

E-24 상위 프로세스는 ChatGPT·codex·codex-computer-use·Installer·Chrome·Docker Desktop 등이었다. 이것만으로 사용자의 수동 조작이나 각 프로세스의 지연 인과를 확정하지 않는다. **아래 절차는 새 측정부터 적용하며 간섭 기준·기존 판정은 바꾸지 않는다.**

1. 구현/빌드/검증/커밋·원본 업로드 준비를 모두 끝낸 뒤, 사용자가 ChatGPT·Chrome 등 앱 완전 종료와 **앱 자동 업데이트 완료 또는 중지**를 확인하도록 요청한다. 전원·최고 성능·절전·Windows 업데이트·WSL 할당도 manifest에 남긴다. 앱 창만 닫았는지와 백그라운드 프로세스 상태는 구별한다.
2. 정식 측정은 Codex/터미널 부모 수명에 묶이지 않은 **분리 실행기**로 시작한다. 시작 전 지연 카운트다운/준비 단계로 사용자가 Codex 창을 종료할 시간을 둔다. 시작 시 실행기 자체가 상위 CPU/메모리·앱 잔존·전원·Docker 상태를 기록한다. 시작 실패는 측정 전 실패로 보존하고 자동 재시작하지 않는다.
3. **측정 중 Codex는 상태 조회·로그 읽기·명령 실행·빌드·파일 작업·진행 메시지 생성을 하지 않는다.** 고정된 호스트/Docker 수집기는 실행기 안에서만 동작한다. 완료까지 외부 상태 확인 없이 대기하고, 앱을 종료했다면 사용자 재개 메시지 후 결과를 읽는다. 현재 도구의 장시간 대기 제약 때문에 주기적 polling으로 대신하지 않는다.
4. 승인된 배경7개는 동일 pause/unpause. 실행기 finally와 별도 watchdog이 성공/실패/중단 모두 복구하고 직접 inspect로7개 running을 확인한 뒤 완료 표식을 원자적으로 남긴다. stop/rm/볼륨변경 금지. watchdog은 Codex가 아닌 실행기 PID를 감시한다. 기동 전 정상/오류/강제 종료 복구를 작은 대역 테스트로 확인한다.
5. 완료 후에만 Codex가 복구·유효성·원본을 읽는다. 기존 CPU>2코어10초·가용RAM<2GiB10초·표본간격>10초·전원변경·미승인 컨테이너 활동 등의 판정은 그대로다. ChatGPT/Chrome 등을 사후 정상부하 목록에 넣지 않는다. 무효가 재발하면 해당 회차 교체 없이 전체 결과를 보존하고 멈춘다.

이번에는 분리 실행기를 구현하거나 이 절차로 측정하지 않았다.

4. 사용자 환경 확인→분리 실행기 실행→Codex 완전 대기→복구 후 결과 검토. 위 기준대로 실패도 보존, 무효 회차 자동 대체 금지.
5. 저장소 요약·manifest·원본 Release·Notion WWHO에 같은 SHA를 연결하고 P3에서 멈춘다. P4/Redis는 결과 후 재결정한다.

공간 근거: [PostGIS &&](https://postgis.net/docs/geometry_overlaps.html)는2D bbox 교차와 인덱스 지원, [ST_MakeEnvelope](https://postgis.net/docs/ST_MakeEnvelope.html)는min/max 직사각형·SRID 의미를 정의한다. [PG17 표현식 인덱스](https://www.postgresql.org/docs/17/indexes-expressional.html)는 표현식 일치와 INSERT/UPDATE 유지비를 설명한다. 현재 데이터·경계에서의 동치와 성능은 구현 후 검증 대상이며 문서만으로 통과를 주장하지 않는다.
